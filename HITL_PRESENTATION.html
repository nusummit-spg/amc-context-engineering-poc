📋 Project Overview

What is HITL?

A Human-in-the-Loop (HITL) feedback system that captures user feedback on query responses, evaluates it using LLM in batches, and automatically applies high-confidence corrections to the Neo4j knowledge graph.

  • Non-blocking feedback capture (< 100ms)
  • Scheduled batch evaluation (hourly)
  • Self-correcting knowledge graph
  • Complete audit trail
  • Token-optimized processing

Key Benefits

  • 70-80% token savings via batch processing
  • Immediate user feedback confirmation
  • Graph learns and improves over time
  • Safe, validated corrections (rollback capable)
  • Production-ready implementation

🔧 Core Components

Feedback Collector

Purpose: Capture and pre-classify user feedback

Responsibilities:

  • Validate response_id exists and is not stale (<24h)
  • Extract entities from feedback text (NER)
  • Classify sentiment (positive/negative/neutral)
  • Score intent/relevance (0.0-1.0)
  • Calculate overall quality score
  • Store in PostgreSQL immediately (non-blocking)
  • Return feedback_id to user (<100ms)

Input:

{ "response_id": "uuid", "session_id": "uuid", "rating": "positive|negative|neutral", "feedback_type": "entity_incorrect|missing|...", "entity_name": "optional", "notes": "optional text" }

Feedback Processor

Purpose: Prepare feedback batches for LLM evaluation

Processing Steps:

  1. Fetch: Get pending feedback from PostgreSQL
  2. Aggregate: Group by entity/type
  3. Consensus: Calculate inter-annotator agreement
  4. Deduplicate: Cluster similar items (40% reduction)
  5. Batch: Create fixed-size batches (25 items)

Output:

List of batches, each containing ~25 feedback items with consensus scores and vote counts.

Batch Evaluator

Purpose: Evaluate batches using LLM with token optimization

Key Optimizations:

  • Shared Context: Fetch Neo4j graph once per batch (not per item)
  • Cached Examples: Few-shot examples cached in Redis
  • Structured Output: JSON schema (no explanation text)
  • Batch Call: 1 LLM call for 25 items (not 25 calls)
  • Vote Counts: Deduplicated items include vote counts

Token Breakdown (25 items):

  • System prompt: 500 tokens
  • Shared context: 800 tokens (1 fetch, 25 items benefit)
  • Few-shot examples: 400 tokens (cached)
  • Item data: 2500 tokens (100 each)
  • Output: 500 tokens
  • Total: 4700 tokens = 188 tokens/item
  • vs Naive: 2100 tokens/item (91% savings!)

Evaluation Orchestrator

Purpose: Schedule and coordinate the 6-step evaluation cycle

6-Step Cycle (Runs Hourly):

  1. Prepare Batches: Aggregate & deduplicate feedback
  2. Evaluate: LLM batch evaluation
  3. Apply: Auto-apply high-confidence corrections (>0.85)
  4. Invalidate: Clear affected caches
  5. Record: Store metrics and audit trail
  6. Cleanup: Archive old feedback, delete rejected

Cycle Duration:

~3 minutes for 500 feedback items (scales linearly)

Graph Corrector

Purpose: Validate and execute corrections to Neo4j graph

Validation Checks:

  • Cypher syntax validation
  • Dangerous operations detection (DROP, DELETE)
  • Business logic validation
  • Entity existence checks
  • Constraint validation

Execution Process:

  1. Capture before state (entity snapshot)
  2. Execute Cypher in transaction (ACID)
  3. Capture after state
  4. Record audit trail
  5. Support rollback via snapshots

💡 Token Optimization Strategies

🎯 Achievement: 70-80% token savings vs naive per-item LLM evaluation

1. Batch Processing

Strategy:

Evaluate 25 items in 1 LLM call instead of 25 separate calls

Savings:

~70% reduction - System prompt amortized across 25 items

Token Reduction: Batch vs Per-Item 70%
70%

2. Semantic Deduplication

Strategy:

Cluster similar feedback items, evaluate representative + vote counts

Savings:

~40% reduction - Avoid evaluating duplicates

Feedback Item Reduction: Deduplication 40%
40%

3. Shared Graph Context

Strategy:

Fetch Neo4j subgraph once per batch, use for all 25 items

Savings:

~50% reduction - Context fetched once, shared 25 ways

Context Token Reduction: Shared vs Per-Item 50%
50%

4. Conditional Routing

Strategy:

Skip LLM evaluation for obvious cases (high/low confidence)

Routing Logic:

  • High Confidence (>0.9): Auto-apply immediately
  • Medium Confidence (0.3-0.9): Send to LLM
  • Low Confidence (<0.3): Reject immediately

Savings:

~60% of feedback never reaches LLM

Feedback Reaching LLM: After Conditional Routing 40%
40%

5. Cached Few-Shot Examples

Strategy:

Pre-compute and cache few-shot examples in Redis (not embedded in prompt)

Savings:

~15% reduction - Few-shot examples retrieved once, reused

6. Structured Output

Strategy:

Use Claude's structured output feature (JSON schema)

Benefits:

  • LLM constrained to JSON (no explanation text)
  • Guaranteed valid output (no parsing errors)
  • No wasted tokens on verbose explanations

Savings:

~30% reduction - Structured output is concise

7. Graph Context Caching

Strategy:

Cache Neo4j subgraph snapshots for 1 hour (Redis)

Savings:

~20% improvement - Faster context fetch, enables batching
