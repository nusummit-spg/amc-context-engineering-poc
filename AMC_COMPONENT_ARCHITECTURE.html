Key Architecture Decisions

ADR-001 — Freeze EvidencePack at response time

  • Immutable D0–D3 snapshot created immediately on response generation
  • All evaluators reference the frozen object — never re-fetch independently
  • Enables reproducible audit trails even as sources evolve

ADR-002 — Deterministic-first, LLM as last resort

  • E0–E5 cascade: stop as soon as decisive result is available
  • LLM invoked for only 2–5% of evaluated interactions
  • 70–80% token savings vs naive approach

ADR-003 — Feedback is a claim, not ground truth

  • Raw feedback → FailureObservation only after adjudication
  • Confidence gate ≥ 0.85 before any auto-apply
  • Feedback poisoning structurally prevented

ADR-005 — Failure-Attribution Graph is separate

  • Two separate Neo4j instances sharing only canonical IDs
  • Zero risk of failure data contaminating answer retrieval
  • Independent access policies and retention rules

ADR-006 — Shadow repair before production

  • All repairs execute in quarantined shadow environment first
  • Regression + compliance + blast-radius tests must pass
  • Atomic promotion or rollback — never direct production write

ADR-008 — Batch LLM evaluation (25 items/call)

  • System prompt amortised across 25 items
  • Semantic deduplication reduces item count by ~40% first
  • Up to 91% token reduction vs per-item evaluation

EvidencePack D0–D3 Breakdown

D0 — Response Finalization (~1ms)

  • response_id (UUID v4 — immutable key for everything downstream)
  • response_hash SHA-256 for tamper detection
  • model_id, model_version, generation_config_version, prompt_template_version
  • citations_shown[], disclosures_shown[], guardrail_state
  • input_tokens, output_tokens, tool_calls[], fallback_used, truncation_flag

D1 — Interaction Snapshot (~1ms)

  • user_query (raw), normalized_query, detected_intent (taxonomy node ID)
  • intent_confidence, intent_detection_method, secondary_intents[]
  • extracted_entities[] with canonical IDs (no raw PII stored)
  • retrieval_configuration, taxonomy_version, guardrail_version
  • session_metadata: user_role, channel, jurisdiction, product_context, client_segment

D2 — Evidence / Provenance Pack (~5ms)

  • Vector: chunk_ids[], similarity_scores[], ranks[], rerank_scores[], document_versions[]
  • Graph: nodes_traversed[], edges_traversed[], paths[], graph_scores[]
  • BM25: bm25_chunk_ids[], bm25_scores[]
  • Context: evidence_selected[], evidence_rejected[], context_token_count
  • 13 pre-computed derived metrics (source_age_days, citation_coverage, source_version_mismatch, etc.)

D3 — Applicability Context (~1ms)

  • jurisdiction + regulated_entity_role + product_type + channel + customer_segment
  • interaction_mode, advice_flag, execution_flag
  • policy_pack_id, policy_pack_version, policy_pack_effective_from
  • applicable_control_set_id, mandatory_controls[], hard_block_controls[]
  • resolution_method: rule | semantic_classifier | ambiguous
🔒
Immutability guarantee Once D0–D3 are created, they are never modified. All evaluators downstream reference the frozen pack. This ensures evaluation is reproducible and audit trails are reliable even after sources, graph edges, or policy packs are updated.

Quality Score Routing Gates

Score < 0.20 → Auto-Reject

  • Set status = 'rejected' immediately
  • Skip evaluation queue entirely
  • Typical: extreme ratings with no comment, duplicate submissions, abuse patterns
  • LLM tokens consumed: 0

Score ≥ 0.95 + cluster ≥ 3 → Auto-Apply

  • High-confidence cluster with strong agreement
  • Bypass LLM evaluation — apply directly in graph correction phase
  • Typical: many users reporting same clear entity correction
  • LLM tokens consumed: 0

Score 0.20–0.94 → Evaluation Queue

  • Set status = 'pending' in PostgreSQL
  • Enters hourly evaluation cycle
  • Will be processed through semantic deduplication → routing → batch LLM eval
  • Accounts for ~60% of all feedback

Background Task Isolation

  • FastAPI BackgroundTasks fires NER + sentiment + intent AFTER HTTP response sent
  • Failure in classification updates classification_status='failed' — does not block feedback record
  • PG UPDATE is a second write — feedback_record exists before classification completes

Orchestration State Machine

Job Status: pending → running

  • evaluation_jobs record created with status='pending'
  • Set to 'running' when Step 1 begins
  • Lock prevents concurrent cycle execution
  • Timeout guard: kill job if >10 min elapsed

Job Status: running → completed

  • All 8 steps complete without unhandled exception
  • Final counts written to evaluation_jobs
  • completed_at timestamp set
  • Prometheus metrics emitted

Job Status: running → failed

  • Unhandled exception caught at orchestrator top level
  • error_message recorded in evaluation_jobs
  • Affected feedback_records remain in 'pending' state for next cycle
  • Alert fired to monitoring system

Incident Short-Circuit (ADR-010)

  • Before routing, check Redis 'incident_active' set
  • Match new feedback observations against active incident signatures
  • Matched items: attach to incident → skip diagnosis → mark processed
  • Prevents duplicate LLM diagnosis during systemic failures
⚠️
Monitoring thresholds pending_feedback_count > 2000 → alert (cycle falling behind). evaluation_cycle_duration > 10 min → alert (batch size or LLM throughput). llm_tokens_per_cycle > 200k → alert (deduplication or routing not working). quality_score_mean < 0.30 trending → possible feedback abuse.

Prompt Structure

SYSTEM (amortised across 25 items)

  • Domain context: AMC chatbot, mutual funds, India/US/EU/UK
  • Output JSON schema (correction_type enum, confidence range, cypher format)
  • Evaluation criteria: what constitutes a genuine graph correction
  • Confidence calibration guidelines

FEW-SHOT (Redis cache, 24h TTL)

  • 2–3 examples per feedback_type
  • Each: input feedback + expected output JSON
  • Covers: entity correction, property update, relationship add/remove
  • Pre-computed, not dynamically generated per call

GRAPH_CONTEXT (Redis 1h / Neo4j)

  • Lightweight subgraph: affected entities + 1-hop neighbours
  • Current property values for relevant entities
  • Existing relationships between affected nodes
  • 200–500 tokens vs 2000+ for full context graph

BATCH (25 items as JSON array)

  • feedback_id, comment, entity_name, rating, quality_score
  • current_graph_state for the specific entity mentioned
  • cluster_size (vote weight from deduplication step)
  • LLM output: [{feedback_id, action, confidence, cypher, correction_type}]
🔑
Confidence threshold (0.85) is a safety gate, not a quality heuristic Items below 0.85 confidence are not discarded — they enter the human review queue (0.50–0.84) or are marked rejected (<0.50). The 0.85 threshold gates automated application only. A human reviewer can still approve lower-confidence corrections through the governance workflow.

🔍 Adaptive Evaluation Router (LLD-04)

The deterministic policy engine that selects the minimum sufficient evaluator for every interaction. Nine stages. Five explicit stop rules. Fifteen standard evaluators. Every decision is auditable via RouterDecision records.

9 Router Stages

🌍
R0 — Resolve Applicability
Resolves the multidimensional applicability key: jurisdiction + regulated_entity_role + product_type + channel + customer_segment + interaction_mode + policy_pack_version. Outputs ApplicableControlSet with mandatory_controls[] and hard_block_controls[]. Deterministic lookup — never LLM.
Rule lookupNo LLM
🚨
R1 — Mandatory Controls
Executes all controls from applicable_control_set mandatory_controls[]. These always run regardless of budget or sampling settings. Failure actions: BLOCK, SAFE_FALLBACK, REFUSE, HOLD_FOR_REVIEW, ALLOW_WITH_DISCLOSURE. Mandatory bypass count must be 0 (hard target).
Always executesC01–C14 mapped
📡
R2 — Signal Dimensions
Computes 10 independent risk dimensions: intent_risk, regulatory_risk, factual_risk, evidence_risk, temporal_risk, citation_risk, response_risk, system_risk, feedback_signal, incident_signal. Each HIGH/MEDIUM/LOW/UNKNOWN. Never collapse into a single score — dimensions must remain explicit.
10 dimensionsRule-based signals
📊
R3 — Evidence Sufficiency
Checks evidence_status from D2: SUFFICIENT (proceed), PARTIAL (attempt bounded recovery), MISSING (deterministic recovery or UNVERIFIABLE), CONFLICTING (conflict workflow), TEMPORALLY_UNCERTAIN (source version resolution). Critical rule: UNVERIFIABLE is a valid and correct verdict.
UNVERIFIABLE allowedNo LLM for missing evidence
🎯
R4 — Active Incident Match
Checks new failure observation against active incidents in the Failure-Attribution Graph (via Redis set). Correlation keys: source_id, source_version, scheme_id, model_version, taxonomy_node_id, time window. Match → attach to incident → skip all remaining stages. Prevents duplicate diagnosis.
Short-circuit on matchADR-010
📏
R5 — Select Minimum Eval Depth
Selects the cheapest evaluator capable of resolving the question from the Evaluator Capability Registry. Maps failure families to evaluator IDs. E0 for infrastructure, E1 for deterministic rules, E2/E3 for semantic, E4 for bounded LLM, E5 for agent/human. Never select a more expensive evaluator than needed.
E0–E5 ladderRegistry-based
💰
R6 — Token/Latency Budget
Assigns token budget band B0–B5: B0=0 (rules), B1=250, B2=500, B3=800, B4=1500, B5=human-approved exception. Enforces hard latency constraints: critical intercept <40ms sync; LLM evaluation is always async. Budget overrun is a first-class failure (F14).
B0–B5 bandsHard latency limits
▶️
R7–R8 — Execute + Stop Rules
Fires selected evaluators. After each result, checks 5 stop rules: STOP-1 (deterministic proof), STOP-2 (evidence absent → UNVERIFIABLE), STOP-3 (known incident), STOP-4 (semantic model resolves), STOP-5 (compliance requires human). Terminates as soon as any stop rule fires.

Emits one RouterDecision record per execution. Stores: selected/skipped evaluators with reasons, stop_reason, token_budget_band, actual tokens and latency, active_incident_matches, signal_dimensions. This is the primary audit artifact answering "why was X evaluated at depth Y?"

🛠️ Self-Healing RAG — 3 Levels + 12 Recipes (LLD-06)

Self-healing is a state-reconciliation problem, not an agentic reasoning problem. Source manifest → actual index/graph diff → recipe selection → shadow execution → atomic promotion. Level 1 and 2 repairs target >90% of cases with zero LLM tokens.

3 Healing Levels

Level 1 — Mechanical Healing (LLM = 0)

  • Retry failed ingestion on non-zero exit code
  • Restore from backup snapshot if index corrupt
  • Re-embed missing chunks (manifest vs index diff)
  • Re-index missing documents from source registry
  • Deduplicate chunks (duplicate_source_ratio > threshold)
  • Repair metadata fields (manifest vs index metadata diff)
  • Expire stale embeddings (source_hash ≠ embedded_hash)

Level 2 — Knowledge-Structure Healing (Mostly deterministic)

  • Entity canonicalization (duplicate canonical ID detected)
  • Graph constraint repair (missing mandatory relationship)
  • Source version reconciliation (vector v17, graph v18 mismatch)
  • Temporal relationship management (two active edges same attribute)
  • Expire superseded graph edges (new source version ingested)
  • Recreate known derived relationships (orphan node detected)

Level 3 — Semantic Healing (Escalation cascade)

  • Rules → semantic classifier → bounded LLM → agent → human SME
  • Used only when deterministic resolution is not possible
  • Ambiguous relationship type between two entities
  • Conflicting narratives from two authoritative sources
  • Entity that doesn't map to any existing taxonomy node

Shadow Environment (ADR-006)

  • All repairs execute in isolated shadow env first
  • Shadow Vector Index + Shadow Context Graph (production copy)
  • Regression query set: golden, cohort, blast-radius, compliance routing
  • Before ↔ after comparison: retrieval quality, citation, numeric, compliance
  • Fail → rollback, Pass → atomic promotion to production
