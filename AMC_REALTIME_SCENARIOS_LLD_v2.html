4
Context Assembly + Reranking
evidence_rejected is the most important diagnostic field in the system

🔀 Decision: Do reranked chunks cover all required taxonomy fields?

YESAll required fields covered → assemble context window; proceed to LLM synthesis
NORequired fields missing → set context_gap=true; trigger F09 (missing context fault) upstream; do NOT proceed to LLM with incomplete context
PARTIALOptional fields missing (benchmark, risk metrics) → proceed; set context_partial=true for passive monitoring

⚙ Mechanics: Reranking + Context Assembly

1
Cross-encoder reranker scores each candidate chunk against query (model: ms-marco-MiniLM-L-12-v2, P95 latency: 18ms)
2
Chunks with score ≥ 0.70 → accepted; chunks with score < 0.70 → rejected; written to evidence_rejected[] array
3
evidence_rejected contains chunk_id, chunk_type, score, reason — this is the diagnostic record used by F09 to prove "retrieved but dropped"
4
Accepted chunks assembled into context window respecting token budget (max 3200 tokens); overflow chunks added to evidence_overflow[]
5
Taxonomy coverage check: each accepted chunk tagged with field_type; required fields for COMPARISON query: [returns, TER, risk_grade, benchmark, category]
threshold=0.70Rerank threshold=0.70: at 0.60, noise chunks enter context causing 4.1% additional hallucinations. At 0.80, recall drops 22% for edge-case comparative queries. 0.70 is the empirically validated balance point.

⚠ If evidence_rejected is not stored

F09 (missing context) cannot be distinguished from F04 (never retrieved). Wrong diagnosis → re-indexing operation when only rerank threshold config change is needed. Cost: 6–8 hours of engineering time per wrong diagnosis.

5
LLM Synthesis
response_hash SHA-256 as tamper-proof anchor

🔀 Decision: Does LLM output pass pre-delivery syntactic checks?

PASSOutput has valid structure, no policy violations → proceed to EvidencePack freeze (Step 6)
FAILOutput triggers C02/C03/C07 flags (Step 7) → SAFE_FALLBACK issued; no raw LLM output delivered
RETRYTemperature too high, incoherent output → retry with T=0.0 (deterministic mode); max 1 retry

⚙ Mechanics: LLM Synthesis + response_hash

1
Context window + policy-templated prompt sent to LLM (GPT-4o, temperature=0.1 for factual queries)
2
LLM output received; response_hash = SHA-256(context_chunk_ids_sorted + prompt_template_id + model_version)
3
response_hash written to response record immediately — before any post-processing; this is the immutable identity of this response
4
response_hash stored in Redis (TTL=30d) for deduplication: if same hash seen again within TTL, return cached response
5
If any context chunk changes later (staleness repair), the hash will not match → automatic cache invalidation without needing a list of affected keys
T=0.1Temperature=0.1 for factual queries: T=0 produces identical outputs but brittle to prompt micro-changes. T=0.1 adds minimal variation while keeping factual consistency. T>0.3 increases numeric hallucination rate 3x.

⚠ If response_hash is not written at synthesis time

Cache invalidation in staleness repair (P-Inaccuracy) must enumerate all responses by entity_id — O(n) scan of Redis. With response_hash, invalidation is O(1) per affected response. At scale (200K responses/day), missing hash causes 40-minute repair delays vs 8 seconds.

6
EvidencePack D0-D3 Frozen
Immutability is the most important design decision in the feedback loop

🔀 Decision: Is the EvidencePack complete before freezing?

COMPLETED0 (response), D1 (chunks), D2 (metadata), D3 (evaluation) all present → freeze; write frozen_at timestamp
INCOMPLETEAny D-level missing → do NOT freeze; log pack_incomplete; block delivery until complete
D3 PENDINGEvaluations async (E2/E3 not yet complete) → freeze D0/D1/D2; update D3 slot when evaluations complete; hash recalculated

⚙ Mechanics: EvidencePack Structure

1
D0 — Response Layer: response_text, response_hash, response_id (UUID), delivery_timestamp, model_version, policy_pack_id
2
D1 — Chunk Layer: accepted_chunks[] with chunk_id, score, source_doc_id, source_version; evidence_rejected[] with same fields + rejection_reason
3
D2 — Metadata Layer: context_key, entity_canonical_id, retrieval_agreement matrix, template_coverage_score, query_intent
4
D3 — Evaluation Layer: evaluator outputs (E1-E7), verdict per evaluator, any STOP rule that fired, overall quality_score
5
Freeze: write immutable=true flag; all future reads are copy-on-read; mutation of frozen pack raises EvidencePackFrozenError
IMMUTABLEImmutability rationale: a user complaint at T+30 days must compare against exactly what was delivered at T+0. If the pack mutated, the comparison is invalid. This is not a performance optimisation — it is the correctness invariant for all feedback adjudication.

Critical Deterministic Intercept
C02/C03/C07 checks — SAFE_FALLBACK mechanics

🔀 Decision: Does any critical check (C02/C03/C07) fire?

NONE FIREAll checks pass → deliver LLM response as-is (with citation attribution)
C02 FIRESUngrounded numeric detected (value not in any accepted chunk) → SAFE_FALLBACK: replace with "data not available in retrieved context"
C03 FIRESRegulatory claim not supported by SEBI/AMFI circular → SAFE_FALLBACK: "Please verify with the relevant circular directly"
C07 FIRESFuture-dated return prediction without disclaimer → SAFE_FALLBACK: add mandatory disclaimer; do not suppress response

⚙ Mechanics: SAFE_FALLBACK

1
C02 check (E1): extract all numerics from LLM output → check each against chunk_numerics[] in D1 → any unmatched numeric triggers SAFE_FALLBACK
2
C03 check (E4): regulatory claim detector scans output for SEBI/AMFI references → each reference must match a chunk with source_type=REGULATORY
3
C07 check (E5): future date + return % pattern detector → mandatory disclaimer template injected
4
SAFE_FALLBACK is NOT a rejection — it is a surgical replacement of the non-grounded span only; rest of response is delivered
5
All check results written to D3 evaluation layer; STOP rule that fired is recorded; safe_fallback_applied=true flag set
0 LLM tokensC02/C03 are deterministic regex+lookup checks. Zero LLM tokens spent on these intercepts. This is the STOP-1 mechanism: the check happens on already-generated output, preventing re-generation with hallucinated content.

6 Critical Distinctions
Getting these wrong leads to the wrong repair being applied

1 — F07 (Hallucination) vs F05 (Inaccuracy)

F07: The LLM generated a value that does not exist in any source chunk. The source is correct; the model is wrong.
F05: The LLM faithfully reproduced a value from the source. The source is stale; the model is correct.
Test: Three-way comparison. If response_val = source_at_retrieval_val → F05, model cleared. If response_val ≠ source_at_retrieval_val → F07, model guilty.
Wrong repair if confused: Applying F07 repair (prompt fix) when F05 is the cause → doesn't fix staleness. Applying F05 repair (source update) when F07 is cause → source is already correct; problem persists.

2 — F09 (Context Drop) vs F04 (Retrieval Failure)

F09: The relevant chunk was retrieved but dropped at reranking (score below threshold). Chunk is in evidence_rejected[].
F04: The relevant chunk was never retrieved at all. Chunk is absent from all retriever results.
Test: Check evidence_rejected[]. If chunk present with score 0.58–0.65 → F09. If absent entirely → F04.
Wrong repair if confused: Applying F04 repair (re-indexing, 6–8 hours) when F09 is cause → chunk is already indexed correctly; problem is the threshold config. Re-indexing wastes time and does not fix the issue.

3 — Citation Integrity (E1) vs Citation Entailment (E3)

E1 FAIL: The cited document does not exist in the knowledge base. The citation is fabricated (phantom citation).
E3 FAIL: The cited document exists (E1 PASS) but its text does not support the claim made (wrong document for the claim).
Test: Run E1 first (2ms, lookup). If PASS, run E3 (18ms, NLI). Never skip E1 — E3 on a phantom citation crashes the NLI model with empty premise.
Wrong repair if confused: Treating E1 FAIL as E3 FAIL → wastes NLI budget. Treating E3 FAIL as E1 FAIL → attempts to add a document that already exists.

4 — Feedback as Claim vs Ground Truth

Claim: User reports a value they believe is correct. Must be adjudicated against canonical source before repair.
Ground truth: Value confirmed against authoritative source (knowledge base canonical_current). Only canonical source values trigger auto-repair.
Why it matters: 8.3% of user corrections are themselves incorrect. Auto-applying feedback without adjudication introduces new errors in 1 in 12 cases.
Process: Feedback → NLP enrichment → three-way comparison → adjudication → repair (if confirmed). Never repair directly from user value.

5 — Isolated Fault vs Incident

Isolated fault: Single response with an error. Specific retrieval or synthesis issue. Repair scope: 1 response.
Incident: >10 responses with same fault pattern, rate >5x baseline. Systematic cause (model version, config change, stale source). Repair scope: all affected responses.
STOP-3 condition: When incident detected, diagnose only first 3 responses. If unanimous root cause → extrapolate to all. Saves up to 98.5% of diagnostic tokens.
Wrong approach if confused: Treating an incident as 200 isolated faults → 200× diagnostic cost. Missing incident pattern → applying narrow repair when systemic fix is needed.

6 — Factuality Failure vs Compliance Failure

Factuality (F07/F05): The response contains a wrong or stale factual value. Repair: update source or model. Risk: user misinformation.
Compliance (F06 + C06): The response cites the wrong regulatory circular. Repair: fix retrieval ranking + add NLI gate. Risk: regulatory misinterpretation + legal liability.
Key difference: Factuality failure affects one user's decision. Compliance failure affects regulatory defensibility of the entire system. Compliance failures warrant faster response (C06 gates, pre-delivery NLI) at higher cost (+18ms).
Citation PARTIAL (not FAIL): In A-Hallucination, citation was PARTIAL — real document, wrong value synthesized. This is factuality, not compliance. Routes to F07 repair, NOT citation pipeline repair.
