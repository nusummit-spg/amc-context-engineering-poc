The Core Principle

🔑
Feedback ≠ Learning. Evaluation ≠ Learning. Diagnosis ≠ Learning.
The chatbot never directly learns from one user's say-so. The graph changes only via governed weekly batches. The LLM's "learning" is a confidence-scored, TTL-bound context patch — not a weight update. This guards against feedback poisoning, adversarial corrections, and AMC taxonomy corruption while still improving visible behaviour immediately after confirmation.

3.3 — app/engine/postgres_client.py ❌ Missing — Most Critical
The single PostgreSQL client used by all feedback/evaluation modules. Currently the most-blocking absent file. Every class in feedback_collector.py, feedback_processor.py, graph_corrector.py, and evaluation_orchestrator.py depends on it.
🚨
This file unblocks 4 existing modules simultaneously. Once postgres_client.py exists and the 5 tables are created, FeedbackCollector, FeedbackProcessor, GraphCorrectionEngine, and EvaluationOrchestrator can all be wired and tested independently.

Class: PostgreSQLFeedbackClient

Initialisation Design
  • Accepts connection string from Settings.postgres_dsn
  • Uses asyncpg connection pool (min=2, max=20 connections)
  • Pool created lazily on first use — safe to construct before pool opens
  • All methods are async def — no blocking I/O
  • Uses asyncpg directly (not SQLAlchemy) — no ORM overhead in the hot path
Error Handling Design
  • DuplicateFeedbackError — same session_id + response_id within 5 min
  • FeedbackNotFoundError — status lookup for unknown feedback_id
  • Connection pool exhaustion → PoolTimeoutError (asyncpg built-in)
  • All methods log errors and re-raise — no silent swallowing
  • Pool health check on startup: run SELECT 1

3.5 — Response Metadata & Evidence Capture
Every response must produce an immutable evidence snapshot the moment it is generated — before any feedback exists. This is the "Capture Interaction Evidence" node in the architecture diagram. Without it, feedback has nothing stable to point at.
🔒
Immutability guarantee: The interaction_evidence record is written once and never modified. All later evaluation — whether it arrives 5 seconds or 5 months after delivery — references the same frozen snapshot. This prevents evaluators from retroactively judging a response using knowledge that didn't exist at response time.

ResponseMetadata Record — Fields Written on Every Delivery

Identity & Content
  • response_id — UUID v4, already generated in routes/query.py
  • query — original user query text
  • response_text — full LLM answer delivered
  • mode — traditional | contextgraph
  • session_id, turn_index — conversation position
  • created_at — UTC timestamp
Evidence Used
  • retrieved_evidence — list of {source, page, score, snippet} from FAISS
  • graph_paths — top Neo4j edges used in context building
  • taxonomy_nodes — matched taxonomy path from query classifier
  • citations — citation markers present in response text
  • guardrail_state — whether any compliance guardrail triggered
System & Cost Metadata
  • model_id, prompt_version — from engine/config.py (for version correlation)
  • input_tokens, output_tokens, total_tokens
  • query_type — from query_classifier.classify_query()
Latency Breakdown
  • latency_ms_total
  • latency_ms_graph — Neo4j traversal time
  • latency_ms_vector — FAISS retrieval + rerank time
  • latency_ms_llm — LLM generation time

Where the Snapshot Lives

In-Memory Cache (ResponseMetadataCache)
  • Already exists in feedback_collector.py with in-memory fallback
  • TTL: 24 hours — for immediate feedback validation
  • Key: response_id → metadata dict
  • Redis-swappable for multi-instance deployments
  • Purpose: fast validation that response_id is real before accepting feedback
PostgreSQL interaction_evidence (permanent)
  • New table (migration 002)
  • Full record persisted for retroactive analysis
  • Enables: "how many responses in the last 7 days used source version v17?"
  • Enables: post-change measurement — did corrections improve retrieval confidence?
  • Never deleted (compliance record)

Dissatisfaction Follow-up Detection

A passive extension of the Active path. When a user sends a follow-up in chat that reads as dissatisfaction, the system converts it to structured feedback without requiring a thumbs-down click.

Detection Logic — 6 Steps
  1. 1 User sends follow-up in chat — any message after a response has been delivered
  2. 2 Intent classifier scores for frustration — keyword patterns: "that's wrong", "incorrect", "outdated", "not what I asked", repeated rephrasing (≤15 words, <3 turns)
  3. 3 If frustration_score ≥ 0.65 → run same-referent check
  4. 4 Embed follow-up query AND prior response — using existing fastembed model in entity_resolver.py (no new model needed)
  5. 5 If cosine_similarity ≥ 0.70 → same topic confirmed — both thresholds met
  6. 6 Create DissatisfactionSignal → enter evaluation queue with entry_route = 'dissatisfaction_converted'. Treated identically to explicit feedback from this point forward.
3.6 — app/engine/batch_evaluation.py ❌ New — Zero Existing Code
The LLM evaluation step. The only component in the entire Phase 2 pipeline with no existing code. Assigns confidence scores to feedback items and generates Cypher correction recommendations. Designed around 7 compounding token optimisation strategies.
⚡
This is the only truly new component in Phase 2. Everything else is either an existing module that needs wiring, a schema/migration to create, or a configuration change. This class needs to be designed and written from scratch — but it is also the most clearly specified piece.

Token Optimisation — 7 Layers

Layer 1 — Batch Processing −70% tokens

One LLM call for 25 items. System prompt, schema, and evaluation instructions paid once and amortised across all 25. The single biggest saving.

Layer 2 — Shared Graph Context −50% context tokens

Neo4j subgraph fetched once for all affected entities in the batch. Only 1-hop neighbours, not the full graph. Cached in Redis: key graph_ctx:{hash(entity_names)} TTL 1h.

Layer 3 — Cached Few-Shot Examples −15% prompt tokens

Pre-computed correction examples per FeedbackType. Redis key: few_shot:{feedback_type} TTL 24h. Retrieved once per cycle, not per batch call.

Layer 4 — Structured JSON Output −30% output tokens

Uses LLMClient.complete_structured() with JSON schema. No markdown, no explanation prose, no filler in response. Compact array of objects only.

Layer 5 — Conditional Routing 60% skip LLM

Items with quality_score ≥ 0.95 AND inter-annotator agreement ≥ 0.90 are auto-applied before reaching this engine. Items with quality_score < 0.20 are auto-rejected. ~60% of items bypass the LLM entirely.

Layer 6 — Semantic Deduplication −40% item count

Done upstream by FeedbackProcessor before batches are formed. Cluster representatives carry vote weights. Reduces batch count by ~40% before any LLM is called.

Layer 7 — Graph Snapshot Reuse Within-cycle saving

Same graph snapshot reused across all batches in one evaluation cycle. The 1h Redis TTL means the snapshot is built once per hour regardless of how many batches run.

Evaluate the feedback items below and determine whether each represents a genuine
knowledge graph correction. For items that do, generate a safe targeted Cypher mutation.

// OUTPUT FORMAT: JSON array, one object per feedback_id
{
  "feedback_id":      string,

  "confidence":      float  // 0.0–1.0,
  "correction_type": "add_entity | update_property | add_relationship | remove_relationship | null",
  "target_entity":   string,
  "cypher_mutation": string  // MATCH ... SET/MERGE — no DROP, no schema changes,
  "reasoning":       string  // one sentence — stored but never used for routing decisions
}

// GRAPH CONTEXT (1-hop subgraph for all affected entities — shared across 25 items)
{graph_snapshot}

// FEW-SHOT EXAMPLES (pre-cached per feedback_type)

// FEEDBACK ITEMS (JSON array of up to 25 items)

Output Validation

  • Parse JSON response — if malformed, retry once with temperature=0
  • Cypher safety check — reject any mutation containing: DROP, CREATE INDEX, CREATE CONSTRAINT, DELETE without MATCH, REMOVE property on compliance-sensitive nodes
  • Final confidence = LLM confidence × inter-annotator agreement (from FeedbackProcessor)
  • Store each item as a row in correction_recommendations regardless of confidence (pending status, confidence gate applied at application time)
3.7 — Tiered Evaluation Engine (HITL Path)
Routes a feedback claim to the cheapest evaluation tier that can resolve it. Stops as soon as a confident verdict is available. 9 deterministic rule categories run first — only unresolved cases escalate to semantic models and only truly ambiguous cases reach the LLM.

Evaluation Tier Ladder

TIER 1A — Rule Categories0 LLM tokens · Runs first on every feedback item

Nine deterministic evaluators, each emitting: {category, rule_id, verdict: pass|fail|score, threshold, evidence_ref}. All use existing graph_store.py and entity_resolver.py — no new infrastructure needed.

TIER 1B — GNN Structural Plausibility0 LLM tokens · Frozen model · Deterministic at inference

Architecture

  • R-GCN (Relational Graph Convolutional Network) or CompGCN
  • Input: candidate triple (subject, predicate, object) + 2-hop neighbourhood subgraph
  • Output: plausibility score 0.0–1.0 + anomaly flags for neighbourhood patterns
  • Interface: GNNPlausibilityScorer.score(subject, predicate, object, subgraph) → float

Key Constraints

  • Frozen at inference time — fixed weights file, fixed threshold, zero non-determinism
  • Zero LLM tokens — graph traversal + matrix ops only
  • Separate training cadence — retrained as a governed batch job (Phase 3 §4.6), never per-interaction
  • Phase 2 plan: starts as stub returning 0.5 (neutral) until GNN training pipeline is ready in Phase 3
TIER 2 — Semantic / NLI Evaluation~0 generative tokens · Local model · Only if Tier 1 unresolved

Model

cross-encoder/nli-deberta-v3-small (local, no API cost). Already in sentence-transformers which is being added to requirements.

Input

  • Premise: text of relevant source chunks from the frozen interaction_evidence snapshot
  • Hypothesis: user's feedback claim converted to a declarative statement

Output & Routing

  • {entailment: float, contradiction: float, neutral: float}
  • entailment > 0.7 → claim is supported by evidence → PARTIALLY_VALID
  • contradiction > 0.7 → claim conflicts → escalate to Tier 3
  • neutral > 0.7 → evidence doesn't address claim → escalate to Tier 3
TIER 3 — LLM / Agent EvaluatorControlled tokens · Last resort · Only when Tier 1 + 2 can't resolve

Uses LLMClient.complete_structured() with a minimal EvaluationPacket — NOT the full conversation, NOT the full evidence. Only: the disputed claim, the 2 most relevant evidence chunks, the inconclusive rule findings, and the NLI score with the reason it didn't resolve.

✅
The same LLM call structure as batch_evaluation.py but single-item with extended context. Escalation to a human reviewer when: all three tiers return confidence < 0.60, the attribute is compliance-sensitive (risk category, jurisdiction, regulatory text), or two genuinely authoritative sources conflict.
3.8 — Passive Evaluation Path
Runs on 100% of responses. Zero user action required. Invisible to users. Complements the Active path by catching failures that users never noticed or chose not to report.
📡
Key principle: The absence of user feedback is not a signal that the response was correct. The passive path monitors structural signals on every response to detect failures the active path would miss. Together they provide complete coverage: 5–15% of interactions surface via active feedback; 100% are monitored via passive signals.

8 Auto-Signals — Computed on Every Response Delivery

numeric_mismatch
Extract all numbers from response; check each against FAISS chunk numerics. Number in response not in any retrieved chunk → fabricated value.
● HIGH
citation_coverage
Count citation markers in response vs number of source chunks used. Low ratio → unsupported claims.
● MEDIUM
source_version_mismatch
Compare source version in evidence snapshot against current source registry. Stale source used → potential inaccuracy.
● HIGH
retrieval_confidence_low
Min FAISS similarity score in retrieved hits. Low floor → weak evidence grounding.

Cohort Health Monitor (Daily Background Job)

A separate daily job that aggregates passive signals across cohorts and generates alerts for systemic degradation — not just individual response anomalies.

Cohort: Query type × feedback_type

e.g. all direct_lookup × entity_incorrect feedback this week vs the 30-day baseline. Catches systematic entity resolution failures.

Cohort: Entity × date

Correction frequency per entity over time. An entity that generates 3× its historical correction rate is flagged for proactive review.

Cohort: Source version × response count

How many responses used a source version that has since been superseded. Catches ingestion lag before users report stale data.

Alert Thresholds

  • Correction rate for an entity > 3× the 30-day baseline → proactive correction candidate created
  • Source version in active use is > 7 days older than current registry version → source refresh alert
  • Average retrieval confidence for a query cohort drops > 15% week-over-week → retrieval degradation alert

Phase 3 — Self-Correcting Knowledge Graph & Governed Deployment
Three deliberately separated stages: Detection (localise), Evaluation (judge), Resolution (act). Detection cannot cause damage. Evaluation can produce wrong verdicts but cannot change the graph. Resolution is the only stage that writes to production.

🔗
Phase 2 → Phase 3 handoff: Phase 2 generates CorrectionRecommendation records with confidence scores. Records ≥ 0.85 confidence are auto-applied to Neo4j by the existing GraphCorrectionEngine. Records needing deeper verification feed Phase 3 from three entry points: HITL-confirmed feedback, the daily GNN structural sweep, and ingestion-time source conflicts. Phase 3 does not run independently — it is triggered by Phase 2 output.

Why Three Separate Stages?

Detection is safely decoupled

Three very different sources (user feedback, automated sweep, ingestion conflict) all produce the same CorrectionCandidate shape. Detection doesn't judge anything — it just hands off a precisely localised node/edge/triple to evaluation.

Evaluation is safely read-only

Rules, GNN, NLI, and optionally LLM all produce verdicts. Incorrect verdicts are possible — but they cannot modify the graph. Only a Confirmed verdict exits this stage and proceeds to Resolution.

Resolution is safely gated

Confirmed corrections go through offline regression testing, then human governance approval before writing to the canonical graph. The Correction Patch Layer provides immediate reversible improvement while the permanent change awaits governance.

4.2 — Stage 1: Detection
Localise the exact disputed node/edge/triple. Three entry points all produce the same CorrectionCandidate schema. Detection does not judge. It does not modify. It only identifies what needs evaluation.

Three Entry Points

Entry Point 1 — HITL-Confirmed Feedback (from Phase 2)
  • Source: a feedback item that passed Phase 2 evaluation with a correction_needed verdict
  • target_entity and correction_type from correction_recommendations identify the candidate
  • Localisation query: MATCH (n) WHERE n.name = $entity_name RETURN n, [(n)-[r]-(m) | [r, m]]
  • Sets entry_point = 'hitl' on the CorrectionCandidate record
Entry Point 2 — Scheduled GNN Structural Sweep (catches drift with ZERO user complaints)
  • New class: StructuralSweepJob in app/tasks/structural_sweep.py
  • Runs daily as background job — sweeps all nodes added or modified in the last 7 days
  • For each node, asks the GNN: is this triple structurally plausible given its neighbourhood?
  • Triples with GNN score < 0.40 (configurable) are flagged as structural_anomaly candidates
  • This is the mechanism that catches graph drift from ingestion issues — no user needs to notice or report
Entry Point 3 — Ingestion-time Source Conflict
  • During document ingestion (app/ingestion/pipeline.py): when a new entity is extracted, compare against existing nodes with the same canonical identity
  • Example: new source says EntityA.TER = 0.82% but existing graph says EntityA.TER = 0.79%
  • The conflict record includes both versions plus their source provenance
  • No auto-resolution — goes into the same evaluation queue as all other candidates
  • Sets entry_point = 'source_conflict'

4.3 — Stage 2: Evaluation
Determine whether the candidate correction is confirmed, rejected, or ambiguous. Runs three evaluators in order of cost and stops as soon as a confident verdict is available. No graph writes happen in this stage.

Signal Merge Strategy

1️⃣
Rule Categories + GNN (Tier 1) → if confident → STOP
0 LLM tokens. Cheapest. Most cases resolve here.
2️⃣
Semantic NLI (Tier 2) → if confident → STOP
~0 generative tokens. Local NLI model. Runs only if Tier 1 unresolved.
3️⃣
LLM / Agent (Tier 3) or Human → verdict always
Controlled tokens. Last resort. Escalates to human for compliance-sensitive cases.
Confidence Threshold

combined_confidence ≥ 0.80 = "confident verdict" — stops the cascade.

Formula: max(rule_confidence, gnn_score) × semantic_weight + semantic_confidence × (1 - semantic_weight)
where semantic_weight = 0.6 if semantic ran, else 0.0

Escalation to Human — When
  • All three tiers return confidence < 0.60
  • Attribute is compliance-sensitive (risk category, jurisdiction, regulatory text)
  • Two genuinely authoritative sources conflict (not just old vs new — same authority level)

4.4 & 4.5 — Stage 3: Resolution & Governance
Act only on a confirmed verdict. Two paths: Confirmed → Correction Patch Layer (immediate, reversible). Rejected → close with no graph change. Governance is the only path that writes to the canonical knowledge graph.

Path A — Confirmed → Correction Patch Layer

:CorrectionPatch Node (Neo4j)

A separate label on the modified node/edge. Stores the corrected value alongside the original — the patch is an overlay, not a replacement.

  • patch_id — UUID
  • original_value — what the graph says now
  • patched_value — the corrected value
  • confidence — from the verdict
  • provenance — candidate_id + verdict_id
  • TTL — days until patch expires if never ratified
  • status — active | ratified | reverted
LLM Context Override

When hybrid_graphrag() encounters an entity with active :CorrectionPatch nodes, it injects the patched value ahead of raw graph facts, tagged:

[PATCHED - PENDING RATIFICATION]

This is the "LLM learns from feedback" mechanism — it is a context override, NOT a weight update, NOT a permanent graph change. Fully logged and reversible.

✅
Improvement Queue: Confirmed but not-yet-ratified corrections are queued for the weekly governance batch. A CorrectionQueueEntry record links the verdict to the batch. The LLM immediately serves better answers via the patch; the permanent graph change waits for governance sign-off.

Path B — Rejected → Close

The candidate is marked rejected with the rejection reason. No graph change. The candidate remains linked to the original feedback_id — useful for pattern analysis (e.g. an entity that is frequently complained about but corrections are always invalid signals a UI or explanation problem, not a data problem).

4.5 — Governance & Controlled Deployment

The only path that writes to the canonical knowledge graph. Weekly batch. Human approval required. No shortcuts.

3 Regression Gates (all must pass before governance)

1. Golden Set Test

Run known correct Q&A pairs for the affected entity against the graph with the correction applied. All must still answer correctly.

2. Blast-Radius Check

Identify all query types that traverse the affected entity. Run them on a staging copy with the correction applied. Verify no regressions in unrelated entities.

3. Compliance Routing Test

Verify the correction does not change which compliance guardrails fire for the affected entity. A correction that changes SEBI guardrail behaviour is not safe to auto-deploy.

Governance API Routes

GET /api/governance/pending-batch

Returns all corrections that passed regression, grouped by entity type and correction type, ready for human review.

POST /api/governance/batch/{id}/approve

Approves entire batch or individual corrections. Triggers canonical KG update sequence.

POST /api/governance/batch/{id}/reject-item/{correction_id}

Rejects one item, sends remainder to apply.

Canonical KG Update Sequence (on approval)

  1. 1Execute Cypher mutation atomically in Neo4j
  2. 2Remove :CorrectionPatch overlay — the graph now has the canonical value. The [PATCHED] tag disappears automatically from future responses.
  3. 3Mark CorrectionQueueEntry as ratified
  4. 4Write to correction_execution_history with action = 'canonical_applied'
  5. 5Trigger FAISS reindex of affected entities (delete stale embeddings, queue re-embedding)
  6. 6Fire GNNRefreshJob event → schedules GNN retrain for next batch window

Rollback: GraphCorrectionEngine.rollback_correction() already exists in engine/graph_corrector.py. It reads the before_state snapshot from correction_execution_history and generates the reverse Cypher. Rollback also restores the :CorrectionPatch overlay if there was one — so users continue to get the patched value while the rollback is investigated.
4.6 & 4.7 — GNN Training Pipeline & Post-Change Measurement
The GNN structural plausibility scorer must stay in sync with the knowledge graph. It is refreshed on the same governed cadence as canonical updates. Post-change measurement closes the loop — verifying that corrections actually improved outcomes.

4.6 — GNN Architecture & Training

Model Architecture
  • R-GCN (Relational Graph Convolutional Network) or CompGCN
  • Input: candidate triple (subject, predicate, object) + 2-hop neighbourhood subgraph
  • Output: plausibility score 0.0–1.0
  • Interface: GNNPlausibilityScorer.score(subject, predicate, object, subgraph) → float
  • Anomaly flags: neighbourhood patterns that deviate from training distribution
Training Data
  • Positive examples: existing edges in the canonical graph (labelled plausible)
  • Negative examples: randomly corrupted triples (head/tail entity swapped) + confirmed-rejected corrections from Phase 3 evaluation
  • Cold start (Phase 3 initial): random corruptions only. Improves as rejected corrections accumulate.
Training Schedule
  • Full retrain: weekly, after governance batch deploys
  • Incremental update: daily, new positive examples since last full train
  • A/B gating: new version compared against current on held-out eval set before promotion
  • Trigger: canonical KG update fires GNNRefreshJob event → schedules training for next batch window
Inference Guarantee
  • After training, model serialised to disk as a frozen weights file
  • GNNPlausibilityScorer loads the frozen file at startup
  • Never updated mid-run — guarantees determinism at inference time
  • Phase 2 stub: returns 0.5 (neutral) until Phase 3 training pipeline is ready. Interface contract is fixed so downstream tiers work regardless.

4.7 — Post-Change Measurement & Loop Closure

After each correction deployment, a 7-day monitoring window measures whether the change actually improved outcomes. This closes the loop back to evidence capture.

📉 Correction Rate

Did the correction rate for this entity decrease over the next 7 days? If yes — the fix addressed the root cause. If no — the issue may be presentation or UX, not data.

📈 Retrieval Confidence

Did FAISS similarity scores for queries involving this entity improve? Better graph data → better embedding alignment → higher retrieval confidence.

⚠️ Side Effect Detection

Did any new negative feedback appear for the same entity after the correction? New complaints about a corrected entity = the correction had unintended side effects.

♻️
Loop closure: The outcome_record is written to correction_execution_history and feeds back into the cohort health monitor's baseline. If correction rate did not decrease → flagged for human review. The system learns which types of corrections work and which ones need different approaches.

:CorrectionPatch Layer adds latency to hybrid_graphrag()
