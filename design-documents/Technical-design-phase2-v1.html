The Core Principle

🔑
Feedback ≠ Learning. Evaluation ≠ Learning. Diagnosis ≠ Learning.
The chatbot never directly learns from one user's say-so. Not the graph (governed, weekly, batch-approved) and not the LLM either — its "learning" is a logged, confidence-scored, TTL-bound context patch rather than a parameter update. This protects against feedback poisoning, adversarial corrections, and accidental AMC taxonomy corruption — while still letting visible behaviour improve immediately after a confirmed correction.

🚨 The 5 Critical Missing Pieces

All six feedback/evaluation modules are fully coded. They all import from files that don't exist yet. Fixing these 5 gaps unblocks the entire pipeline with zero rewrites.

1️⃣
app/schemas/feedback.py — Pydantic models (FeedbackRequest, FeedbackResponse, EvaluationRecord, enums). Referenced by every feedback module. Without this, no module can even be imported.
2️⃣
app/engine/postgres_client.py — PostgreSQLFeedbackClient. Referenced as a dependency by all 4 feedback modules: FeedbackCollector, FeedbackProcessor, GraphCorrectionEngine, EvaluationOrchestrator.
3️⃣
app/engine/batch_evaluation.py — BatchEvaluationEngine. The LLM evaluation step. Zero existing code. The only component in the entire pipeline that needs to be written from scratch.
4️⃣
PostgreSQL schema + migrations — The migrations/ directory exists but is empty. 5 tables needed: feedback_records, feedback_classifications, evaluation_records, correction_recommendations, correction_execution_history.
5️⃣
Wiring in app/api/deps.py + startup in app/main.py — The Container class has no feedback attributes. The APScheduler is never started. The feedback router is never registered. All this just requires adding ~20 lines to existing files.

What "Blocked" Means in Practice

⚠️
FastAPI will currently fail to start if any of the feedback routes are registered, because from app.schemas.feedback import FeedbackRequest raises ModuleNotFoundError. The routes are deliberately excluded from main.py right now. Fixing gap #1 (schemas) immediately enables the imports, and fixing gaps #2–5 in order completes the pipeline.

How Phase 2 Feeds Phase 3

🔗
Phase 2 generates CorrectionRecommendation records in PostgreSQL with a confidence score. Records above 0.85 are automatically applied to Neo4j by the GraphCorrectionEngine (already written). Records that need deeper verification (Phase 3 KG correction pipeline) come from three sources: HITL-confirmed feedback from Phase 2, the GNN structural sweep, and ingestion-time source conflicts. Phase 3 is triggered by Phase 2's output — it does not run independently.
